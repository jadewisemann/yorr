# 조별과제 야트 다이스 규칙과 완성 상태

> Jira: S15P11A406-209 · 게임 코드 `TEAM_YACHT` · 온라인 3인 정확히 한 팀 · 라우트 `/team-yacht`

**Jira 티켓 본문에는 아직 "규칙 미확정"이 남아 있다.** 규칙은 구두로 확정되었고, 이 문서가 그
확정 내용을 기록하는 유일한 곳이다(MR 설명에도 사본이 있다). 판정의 SSOT는 서버
[`TeamYachtRules.java`](../../../backend/src/main/java/com/ssafy/yorr/game/teamyacht/TeamYachtRules.java)다 —
이 문서와 코드가 어긋나면 코드가 이긴다.

## 핵심 착상

일반 야추의 "1라운드 = 한 사람이 최대 3굴림"을 **"1라운드 = 3명이 각각 1굴림"** 으로 치환한다.
`SEATS = 3`, `ROUNDS = 12`, `DICE_COUNT = 5`. 점수 계산은 일반 야추와 완전히 같고
[`yacht-rules.md`](./yacht-rules.md)의 12족보·상단 보너스가 그대로 적용된다 — `scoring.ts`는
서버와 공유하는 SSOT라 **한 줄도 건드리지 않았다**.

3인이 **점수판 하나를 공유**한다. 12라운드를 끝내면 팀 총점이 결과다.

## 라운드 진행

| 순번 | 하는 일 |
|---|---|
| **1번 주자** | 5개 전부 굴린다 → **1~3개**를 킵 |
| **2번 주자** | **앞 사람이 킵한 주사위의 값만 보인다.** 앞 사람이 무엇을 버렸는지는 알 수 없다. 앞 사람의 킵은 **해제 불가**. 가려진 주사위를 굴린 뒤 **1개 ~ (남은 수 − 1)개** 킵 |
| **3번 주자** | 남은 걸 굴린다. 마지막 굴림이라 킵 선택 없이 5개가 확정된다 |

**기록은 다수결.** 3명이 각자 족보 하나를 지목하고 **2표 이상** 받은 족보에 기록한다.
전원이 다른 족보를 부른 동표(1:1:1)면 **룰렛으로 랜덤 결정**한다.

**매 라운드 주자 순서가 한 칸 로테이션된다**(`rotateSeats`). 12라운드면 각 좌석을 정확히 4번씩
맡는다.

### 무임승차 방지 = 킵 강제

1번 1~3개 / 2번 1개~(남은 수−1)개 / 3번 나머지 전부(`keepBounds`·`isValidKeep`).
**아무것도 킵하지 않고 다음 사람에게 넘길 수 없다.** 3번 주자가 굴릴 주사위도 항상 최소 1개
남는다. 별도 감점 규칙은 없다 — 이 제약 하나로 전원 기여가 보장된다.

검증은 **서버에서** 한다. 클라이언트 검사는 되돌릴 조작을 미리 막는 거울일 뿐이다.

## 숨긴 정보를 지키는 경계

**버린 주사위의 눈은 `TeamYachtView`에 애초에 담기지 않는다**(해당 자리가 null). 프론트에서
가리는 방식은 쓰지 않는다 — 개발자 도구로 다 보인다. 상태는 개인 메시지로만 방송된다.

## 룰렛(동표 처리)이 결정론이어야 하는 이유

**랜덤은 서버가 결정하고, 결과와 시드를 내려보낸다.** 클라이언트 애니메이션이 결과를 정하면
클라이언트마다 다른 족보에 멈춘다. 클라이언트는 "룰렛이 돌다가 서버가 정한 항목에서 멈추는"
연출만 담당한다.

난수는 프론트 `dice.ts`의 `nextRollSeed`와 **같은 LCG**를 쓴다(`LCG_MULTIPLIER = 1664525`,
`LCG_INCREMENT = 1013904223`, `MODULUS = 2^32`). 프론트 `rouletteWinner`/`nextSeed`와 서버가
같은 시드에서 같은 값을 내는 것을 양쪽 테스트가 덮는다.

## 구조 결정 — 기존 야추를 건드리지 않는다

**별도 게임 코드 `TEAM_YACHT`의 신규 모듈**로 등록했다. 기존 `YACHT_DICE` 모듈과
`game/yacht/**`는 무변경이다. 완료 조건의 "일반 야추 회귀 없음"을 구조적으로 보장하기 위한
선택이다 — 순차 킵·숨긴 주사위·다수결을 기존 `RoundState`에 끼워 넣으면 일반 온라인 야추가
깨진다.

이 브랜치의 diff는 **`+2360 / −0`** 이다. 기존 코드를 한 줄도 수정하지 않았다.

## 진입 경로

**랜딩 카탈로그에 넣지 않는다**(제품 결정). `/team-yacht` 라우트가 방 생성·대기실·플레이를 다
들고 있고, 초대는 `?code=`로 붙는다.

`/rooms/:id/lobby`·`GamePage`를 경유하지 않는 이유: 그 화면들은 `games.ts`의 `GameCode` 유니온으로
게임을 고르는데, `games.ts`는 병렬 작업(210) 소유라 건드릴 수 없었다 → 카탈로그에 없는 코드는
그 길로 자기 화면에 도달할 수 없다. 소켓은 앱의 `RealtimeSync`를 그대로 쓴다.

## ⚠️ 추가로 필요한 작업

### 1. 백엔드 컴파일·테스트 검증 (최우선 · 병합 전 필수)

**`game/teamyacht/**` 의 Java 8파일(~1050줄)은 한 번도 컴파일된 적이 없다.** 작업 환경에 JDK가
없었다(`java`/`javac` 부재, `JAVA_HOME` 미설정).

```bash
cd backend && ./gradlew test --tests '*TeamYacht*'
```

`TeamYachtRulesTest`(13케이스)가 12라운드 완주·좌석 4회씩·킵 경계·다수결·룰렛 결정론을 덮는다.
**이걸 통과시키는 것이 병합의 최소 조건이다.**

컴파일 없이 손으로 검토하는 과정에서 실제 버그 1건을 잡았다(`List.of().contains(null)` → NPE,
커밋 `74e0c42`). **눈으로 하나가 잡혔다는 건 안 잡힌 게 더 있을 수 있다는 뜻이다.**

### 2. 실제 3인 동시 접속 완주 미검증

백엔드·Redis를 띄울 수 없어 검증하지 못했다. 대신 확보한 것:

- 프론트 통합 테스트가 실제 화면·라우터로 **12라운드를 완주**한다(계약대로 응답하는 서버 대역
  사용: 내 굴림·킵 → 팀원 2명 자동 진행 → 투표 → 로테이션 → 종료 화면·총점)
- 서버 규칙은 `TeamYachtRulesTest`가 덮는다 — **단 이 Java 테스트는 실행되지 않았다**

JDK 확보 후 3인 실접속 1회가 필요하다. 특히 **개인 메시지 경로**(각자 다른 시야)와 **가려진
주사위**가 실제 소켓에서 의도대로 갈라지는지가 테스트로 덮기 어려운 지점이다.

### 3. `wsEvents.ts` 머지 충돌 (예정된 것)

라이어스 다이스(210, MR !175)와 `frontend/src/realtime/wsEvents.ts`에서 충돌한다. 나중에 머지하는
쪽이 해소한다 — 양쪽 다 유니온 타입에 항목을 추가하는 것뿐이라 **양쪽 항목을 모두 유지**하면
된다. 서로의 계약을 지우지 않도록 주의.

### 4. `GameCode` 유니온 정리 (후속 과제)

`roomApi.ts`의 `isGameCode`가 카탈로그 기반이라, 카탈로그에 없는 `TEAM_YACHT`를 넘기려면
`gameCode: 'TEAM_YACHT' as GameCode` 캐스트가 화면 경계에 1줄 있다(주석 있음). 210이 그 검증을
`games.ts`에서 파생시키는 쪽으로 고쳤으니, **210 머지 후** 이 캐스트를 없애는 정리가 가능하다.

### 5. 턴 마감 타이머

일반 야추의 `RoundTimerService`(오프라인 스킵 → N회 후 자동 퇴장)를 이 모듈이 그대로 쓰는지
확인되지 않았다. 3인 중 한 명이 조작하지 않으면 라운드가 멈추는지 실접속에서 확인이 필요하다.
