# 크로스 스택 디버깅 — 프론트 증상에서 서버 원인까지

## 메타데이터

| 항목 | 내용 |
|---|---|
| 키워드 | 지연 보상, 레이스 컨디션, 스케줄러, 근본 원인 분석, 롤백 판단, Java/Spring |
| 핵심 커밋 | `a83c6fe`(스윙 지연 보상, BE) · `7b7dc2e`(스케줄러 레이스, BE) · `8f9f52f`(배포 회귀 롤백) |

프론트 담당이지만 증상이 프론트에 나타나도 원인이 서버면 서버까지 갔다.
세 사례 모두 커밋 메시지에 정량 분석이 남아 있다 (`git show <hash>`).

## 사례 1 — "완벽하게 맞춘 스윙이 네트에 걸린다" (`a83c6fe`)

- **증상**: 탁구에서 눈으로 완벽하게 타이밍을 맞춘 스윙이 네트 판정.
- **분석**: 서버가 메시지 **도착 시각**으로 판정해 업링크 지연이 통째로 "늦게 침"이
  됐다. 수치로 증명 — 스위트스팟 0.9에서 네트 판정 시작 1.02까지 여유가 0.12뿐이라,
  보통 속도 1.0 pos/s에서 **120ms 지연이면 판정창을 통째로 벗어난다**(스매시 리턴은
  62ms). 모바일 업링크에서 일상적인 지연폭이다.
- **해결**: 클라가 이미 payload에 싣고 있었지만 **아무도 읽지 않던 `clientTs`**를 판정
  시각으로 사용. 되감기 폭을 120ms로 캡해 미래 스윙·죽은 공 치기를 차단. 클라 변경 0줄.
  한계(클라 시계가 뒤지면 공짜 되감기 최대 120ms)와 근본 해법(상대 시간 전송)까지
  주석으로 남김.

## 사례 2 — "공이 화면에서 얼어붙는다" (`7b7dc2e`)

- **증상**: 탁구 진행 중 공이 멈추고 방 전체가 영영 정지.
- **분석**: 마감 스케줄러(`InMemoryRoundDeadlineScheduler`)의 레이스 — `schedule()`이
  `executor.schedule()`을 먼저 부르고 맵 슬롯을 나중에 등록했다. **마감이 이미 지나
  delay가 0이면** 워커가 그 사이에 깨어나는데 맵에 자기 세대가 없어 조용히 스킵 → 그
  방은 다음 schedule까지 타임아웃이 영영 안 온다. delay 0이 흔한 이유까지 추적:
  `TOO_LATE` 판정은 정의상 미스 마감 40ms 전에 발생하고, 그 갈래가 옛 마감을 그대로
  넘긴다. **야추도 같은 스케줄러를 쓴다** — 파급 범위까지 확인.
- **해결**: 슬롯을 예약보다 먼저 잡고 future는 예약 뒤에 붙인다. 이미 실행돼 슬롯이
  비었으면 붙일 것이 없다. 스케줄러 단위 테스트 +86라인.

## 사례 3 — 데모 직전의 롤백 판단 (`8f9f52f`)

- **상황**: 404파일 규모 리팩터링 MR 병합 후 배포 환경에서 회귀 3건(탁구 폰 컨트롤러
  무반응 · 탁구/야추 진동 소실).
- **판단**: 원인 조사로 3건 중 2건의 원인 커밋을 특정했지만(컨트롤러 지연 보상 부재,
  햅틱 12ms 단독화로 안드로이드 미렌더), 1건은 미확정 — **데모가 가까워 원인 확정을
  기다리지 않고 마지막 정상 상태로 되돌리는** 결정을 내렸다.
- **엔지니어링 디테일**: 내용은 사라지지 않는다 — 원본 커밋과 브랜치를 보존하고,
  "되살릴 때는 이 커밋을 revert하라(브랜치 재병합은 '이미 머지됨'으로 취급돼 아무것도
  안 들어온다)"는 git 동작 원리까지 커밋 메시지에 문서화했다.

## 활용 포인트

- "판정 로직의 지연 민감도를 수치로 계산해(판정창 0.12 pos ÷ 1.0 pos/s = 120ms) 서버
  판정 시각을 클라이언트 타임스탬프 되감기로 교체 — 클라 변경 없이 밸런스 문제 해결"
- "재현이 어려운 '방 멈춤'을 스케줄러의 등록 순서 레이스로 특정하고, delay 0이 흔한
  도메인 조건까지 역추적해 수정"
- "데모 직전 회귀에서 원인 확정 대기 vs 롤백의 트레이드오프를 판단하고, 복구 경로까지
  문서화한 의사결정 경험"

## 예상 꼬리 질문

- **프론트인데 왜 서버를 고쳤나?** 증상의 소유자가 원인의 소유자를 기다리면 사용자만
  기다린다. 계약(wsEvents)을 양쪽에서 다뤄 서버 코드 진입 장벽이 낮았고, 수정은 테스트와
  함께 백엔드 리뷰를 거쳤다.
- **레이스를 어떻게 재현했나?** 재현이 아니라 코드 경로 분석 — TOO_LATE의 발생 시점
  정의(마감 40ms 전)에서 delay 0이 필연임을 증명하는 방식으로 접근했다.
