## 문제

주사위 값은 공정성을 위해 **서버가 정한다**. 그런데 물리로 실제로 굴리면 멈춘 면이 서버
값과 다르고, 미리 만든 애니메이션은 흔들기 세기·던지는 각도가 반영되지 않아 "내가
굴렸다"는 감각이 죽는다. 부가로 주사위 겹침(관통), 슬로모션 같은 낙하, 영영 안 멈추는
굴림, 관전자 화면에서 결과가 먼저 보이는 순서 역전이 QA에서 반복 제보됐다.

## 해결 (설계 결정 4가지)

1. **던지는 순간 한 프레임 안에서 끝까지 미리 굴린다.** Rapier 월드 스냅샷을 복제해
   480Hz로 동기 시뮬 → 자연 착지 눈과 60fps 궤적을 함께 확보하고, 화면은 그 궤적을
   재생만 한다. 예측용/화면용 월드를 따로 굴리면 충돌 오차가 카오스적으로 증폭되어 다른
   면이 나오므로 **두 번째 시뮬레이션을 만들지 않는 것**이 핵심. 예측 상한을 제품의 강제
   종료 시간과 일치시켜 최악의 프레임 지연을 계산 가능하게 묶었다.
2. **큐브 대칭 회전으로 서버 값을 입힌다.** 목표면 법선→자연면 법선의 90°/180° 오프셋
   쿼터니언을 `mesh.quaternion = body.rotation × offset`으로 렌더링에만 곱한다 — 물리는
   자연스럽게 멈추고 화면에는 서버 값이 위를 향한다.
3. **물리 닮음(dynamic similarity)으로 낙하 속도를 튜닝했다.** 축척이 실물의 47배라
   1/15 슬로모션이었는데, 중력만 올리면 비행 중 회전이 반토막 나는 것을 실측으로 확인 —
   `GRAVITY_SCALE` 노브 하나에서 속도 ×√k / 시간 ÷√k / 거리 불변으로 전 상수를 유도해
   "같은 움직임을 √k배 빠르게 재생"으로 풀었다. 겹침은 60→480Hz + soft CCD로 관통 깊이를
   0.284→0.073으로 줄여 해결.
4. **관전자 동기화를 이벤트로 풀었다.** `dice.throw/thrown`(던진 시점), `dice.shake/shaken`
   (흔들림 펄스)을 계약에 추가(v0.6–v0.7) — 그전에는 굴린 사람이 흔드는 중인데 관전자
   화면에 결과가 먼저 보였고, 손을 멈춰도 관전 화면만 계속 흔들렸다. 모든 클라이언트가
   서버 사실에서 파생한 같은 시드(FNV-1a)를 쓰므로 연출까지 동일하다.

안전망: 시간 기준 정착 판정(0.12초), 시드 결정론적 재시도 최대 3회, 엣지 스탠딩 눌러
앉히기, 사발/트레이 봉쇄(복제 시뮬에도 동일 적용), 상한 조기 마감(결과는 이미 확정이라
점수 불변).

## 결과

- QA 반복 제보되던 주사위 버그(겹침·미정착·순서 역전·슬로모션)가 소멸
- 같은 파이프라인이 튜토리얼·레버리지 모드와 파티 대시보드 관전에 그대로 재사용됨
- 물리 코드에 단위 테스트 47개+ 확보 — jsdom에 WebGL이 없어 렌더러 대역
  (`FakeWebGLRenderer`)을 만들어 장면·카메라·물리를 실제로 돌린다

## 예상 꼬리 질문과 답의 뼈대

- **왜 서버에서 물리를 안 돌리나?** 서버는 값만 정하면 충분하다. 물리는 연출 품질
  문제라 클라 프레임레이트에 맞추는 편이 낫고 서버 비용도 없다.
- **예측 시뮬이 메인 스레드를 막지 않나?** 상한 = 제품 최대 굴림 시간으로 묶어 최악
  지연이 유계다. 개선 여지(워커 분리)도 인지하고 있다.
- **리맵이 눈에 띄지 않나?** 축 정렬 법선 간 회전이라 90°/180° 스냅이고, 움직이는 동안
  물리 회전에 곱해지는 상수 오프셋이라 구분이 불가능하다.
- **결정론은 어떻게 보장하나?** 시드가 서버 사실(방·플레이어·라운드·굴림수·주사위)의
  해시라 모든 클라이언트가 같은 난수열·같은 재시도 섭동을 얻는다. `Math.random()` 없음.

## 활용 포인트

  오프셋으로 서버 권위 주사위 값을 물리 연출 위에 입히는 파이프라인을 설계·구현"

  이유'를 실측으로 증명"
