## 1. 도메인 우선 구조 재편 (236파일, 하루 만에 무사고)

레이어 우선 구조에서는 야추 하나를 이해하려고 7개 폴더 + `src/` 루트(19개 파일 산재)를
동시에 뒤져야 했고, `components/`에 랜딩 카드·야추 게임판·로비 패널·공용 버튼이 평평하게
섞여 있었다. `src/<도메인>/<레이어>`로 재편해 **게임 추가 = 폴더 하나**가 됐다 — 실제로
탁구·석양이 진다가 이 구조 위에 각각 독립 폴더로 들어왔다.

- 의존 방향을 사용자 흐름 순서의 단방향(`app → landing → room → yacht`)으로 선언하고
  **dpdm으로 CI에서 강제**. 경계 모듈(`shared`·`realtime`·`games.ts`·`store.ts`)만 예외.
- 지키지 못한 경계 2건(계약이 야추 모양인 `wsEvents`, 결과 화면의 room API 직접 호출)은
  숨기지 않고 **파일 주석 + 문서 + 티켓**으로 남겼다 — "게임 추가를 실제로 막는 것은
  폴더가 아니라 프로토콜"이라는 진단까지.
- 상태 설계 원칙: 서버 권위 상태(WS만 변경) / 로컬 UI 상태(라운드에 귀속) / 파생 상태
  (계산하고 저장 안 함 — 세션 FSM이 대표 사례).

## 2. 디자인 시스템 — 토큰 2계층과 근거 있는 규칙

- **원시값(`--ds-*`) → semantic 토큰(`@theme inline`)** 2계층. 테마 교체 = 원시값 블록
  교체. 컴포넌트는 `bg-[#…]` 금지, `bg-canvas`·`min-h-tap`만.
- **`cn()`에 커스텀 토큰을 등록해야 하는 이유를 규명** — 등록하지 않으면 tailwind-merge
  충돌 그룹에 못 들어가 기본값과 override가 둘 다 살아남고, 승자를 빌드된 CSS 선언
  순서가 정한다. "외부 배치는 className으로 확장한다"는 규칙의 성립 조건.
- **레시피는 `@utility`가 아니라 `@layer components`** — v4 레이어 순서상 레시피가 항상
  인라인 유틸리티에게 지도록. 도입 기준도 정량: 렌더된 DOM에 5회 이상 반복(게임 화면
  HTML 34.5KB 중 31%가 중복 class 문자열이었다는 측정에서 출발).
- **모션 이원화의 경계를 성능 원리로 정의** — 장식·반복은 CSS keyframes(컴포지터,
  물리 시뮬과 프레임을 다투지 않음), 진입·퇴장은 motion(AnimatePresence가 필요). "돌아가는
  CSS 애니메이션을 motion으로 옮기지 마라"가 규칙이 된 이유까지.
- 접근성: 명도 대비 4.5:1 재조정, 상태를 색 하나에 싣지 않기(빗금 패턴 이중 채널),
  44px 터치 타깃, live region 프레이밍, 한국어 어절 줄바꿈 전역 규칙.
- 화면 전환을 JS가 아니라 **브라우저 View Transitions**로 — 나가는 화면을 붙잡으면
  stale Outlet이 새 화면을 또 그리고 WebGL/물리 월드가 두 벌 살아나는 문제를 스냅샷
  방식으로 구조적으로 회피. 초기 청크는 랜딩+404만, 나머지는 idle prefetch.

## 3. 문서를 에이전트 친화 위키로

문서 체계도 설계 대상으로 다뤘다 (`db1a6b6` → 현재 `docs/wiki/` 17페이지):

- **인덱스 하나에서 출발, 필요한 페이지만 여는** LLM/에이전트 우선 구조. "표에 없는
  문서는 없는 것과 같다."
- **SSOT 원칙** — 문서와 코드가 충돌하면 코드가 이기고, 각 페이지가 원본 코드 경로를
  가리킨다. 유효기간 있는 자료(스프린트 로그)는 두지 않는다 — git이 보관한다.
- 코드 주석 컨벤션: 수치·정책에는 근거(실측, 티켓)를 남긴다 — 이 저장소의 주석은
  "무엇"이 아니라 "왜"를 말한다.
