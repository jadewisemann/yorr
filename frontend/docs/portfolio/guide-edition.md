## 1. 프로필

### 슬로건

> **"감이 아니라 실측으로 증명하는 프론트엔드 개발자 정유진입니다."**

버그도, 성능도, 아키텍처 규칙도 수치로 근거를 남깁니다 — "중력만 올리면 회전이
반토막 난다"를 실측으로 증명해 물리 튜닝 체계를 다시 세우고, 판정 로직의 지연
민감도를 120ms로 계산해 서버 판정 방식을 바꿨습니다.

### 한 줄 소개

실시간 멀티플레이 웹 게임의 클라이언트 전체를 단독으로 설계·구현하며, **WebSocket
상태 동기화·3D 물리 연출·모바일 센서 입력**을 깊이 있게 다뤄 왔습니다. 프론트 증상의
원인이 서버에 있으면 Java 코드까지 직접 추적해 고치는 개발자로, 단기적으로는 실시간
인터랙션 전문성을, 중장기적으로는 계약(contract) 설계 역량을 갖춘 크로스 스택
엔지니어를 지향합니다.

### 문제해결 사례

#### 사례 1. 서버가 정한 주사위 값 vs "진짜 물리" 연출

- **문제 인식** — 주사위 값은 공정성을 위해 서버가 정하는데, 물리로 실제로 굴리면
  멈춘 면이 서버 값과 다르다. 미리 만든 애니메이션은 흔들기 세기가 반영되지 않아
  "내가 굴렸다"는 감각이 죽는다. QA에서 주사위 겹침·미정착·슬로모션 낙하가 반복 제보.
- **해결 방안** — 던지는 순간 물리 월드를 복제해 **480Hz로 끝까지 미리 굴리고** 화면은
  그 궤적을 재생. 서버 값은 큐브 대칭 회전(90°/180° 쿼터니언 오프셋)을 렌더링에만 곱해
  입힌다. *이 방법을 선택한 이유*: 예측용/화면용 시뮬을 따로 돌리면 충돌 오차가
  카오스적으로 증폭돼 다른 면이 나온다 — "두 번째 시뮬레이션을 만들지 않는 것"이 핵심.
- **개선 성과** — 관통 깊이 **0.284 → 0.073** (60→480Hz + soft CCD), 슬로모션은 물리
  닮음 원리로 상수 체계를 재유도해 해결(중력만 올리면 비행 중 회전이 반토막 나는 것을
  실측 증명). QA 반복 제보 버그 소멸, 같은 파이프라인이 연습 모드·관전 화면에 재사용.

#### 사례 2. "완벽하게 맞춘 스윙이 네트에 걸린다" — 판정의 지연 민감도

- **문제 인식** — 탁구에서 타이밍이 완벽한 스윙이 네트 판정. 판정창을 계산해 보니
  스위트스팟 여유 0.12 pos ÷ 공 속도 1.0 pos/s = **120ms**. 서버가 메시지 도착 시각으로
  판정해, 모바일에서 일상적인 업링크 지연이 통째로 "늦게 침"이 되고 있었다.
- **해결 방안** — 클라가 이미 보내고 있었지만 아무도 읽지 않던 `clientTs`를 판정 시각으로
  사용(서버 Java 코드 직접 수정). *이 방법을 선택한 이유*: 판정창을 넓히면 게임이
  물러지지만, 시각 기준을 바꾸면 밸런스를 유지한 채 지연만 제거된다. 되감기 폭을 120ms로
  캡해 미래 스윙·죽은 공 치기를 차단.
- **개선 성과** — **클라이언트 변경 0줄**로 회선 품질과 무관한 공정한 판정. 남은 한계
  (클라 시계 조작 시 최대 120ms 이득)와 근본 해법까지 주석으로 문서화.

#### 사례 3. 모바일 브라우저는 수시로 끊긴다 — 세션 복구 체계

- **문제 인식** — 백그라운드 전환·화면 잠금·터널에서 WebSocket이 수시로 끊긴다. 끊긴
  사람의 턴이 방 전체를 멈추면 안 되고, 돌아온 사람은 점수판·굴림 진행을 그대로
  이어받아야 하며, 브라우저를 껐다 켜도 방으로 돌아와야 한다.
- **해결 방안** — ① 세션 상태를 저장하지 않고 `(세션, 스냅샷)`에서 **파생하는 순수 함수
  FSM** (*이유*: 저장하면 두 소스가 어긋나는 순간 유령 세션이 생긴다) ② `sessionToken`
  기반 재입장 + 서버 측 정체성 복원을 **서버(Java)까지 직접 구현** ③ 스냅샷 병합
  불변식을 WS/REST 양쪽에 대칭 적용 ④ localStorage 40분 영속화(서버 방 TTL과 일치) +
  복귀는 사용자가 "이어서 하기"를 누른 뒤에만.
- **개선 성과** — 새로고침·브라우저 재시작·네트워크 단절 모두에서 **점수판 손실 없이
  복귀**. "REST 응답이 게임 종료 이벤트를 덮어 결과 화면이 안 뜨는" 실측 레이스 제거.
  재접속 6 + 단절 4, E2E 10스펙으로 회귀 방지.

#### 사례 4. 아이폰에서만 던지기가 안 된다 — iOS 편차의 실측 규명

- **문제 인식** — 같은 코드가 갤럭시에서는 되고 아이폰에서는 던지기 제스처가 인식되지
  않았다. 소리도 아이폰 관전자에게만 안 났다.
- **해결 방안** — 실기기 계측으로 **iOS Safari의 가속도 부호 규약이 Chrome과 반대**임을
  규명, 판정을 "한 축을 따라 날카롭게"라는 본질로 재정의해 절댓값 기반으로 수정. 오디오는
  iOS가 `<audio>` 요소별로 제스처 이력을 따로 기억하는 것을 확인하고 앱 부팅 시 모듈
  레벨에서 생성. *이 방법을 선택한 이유*: UA 분기로 부호를 뒤집는 임시 대응은 다음 편차에서
  또 깨진다 — 판정 정의 자체를 플랫폼 무관하게 바꾸는 쪽이 구조적이다.
- **개선 성과** — iPhone Safari에서 던지기·효과음 정상 동작. 재현이 어려운 센서 문제를
  위해 **센서 스트림 녹화/재생 튜닝 도구**(`/__dev/motion`)까지 구축해 이후 편차도
  결정론적으로 재판정 가능.

#### 사례 5. CI가 가끔 빨간불 — flake를 재시도로 덮지 않기

- **문제 인식** — CI에서만 간헐적으로 실패하는 테스트. 재시도로 덮으면 진짜 회귀를
  놓치게 된다.
- **해결 방안** — 원인을 하나씩 실측: jsdom에 WAAPI가 없어 퇴장 애니메이션이 안 끝나는
  틈은 motion mock + `initial={false}`로 **틈 자체를 제거**, CI 러너가 로컬의 30배
  느린 것을 측정해 타임아웃을 "실패할 때만 소진되는" 방향으로만 조정. 커버리지가
  흔들리는 유일한 파일은 동일 테스트 2회 실행 비교(90.48% vs 91.43%)로 특정해 근거와
  함께 측정에서만 제외.
- **개선 성과** — **CI 랜덤 실패 0**, 커버리지 래칫(구문 96 / 분기 91 / 함수 96 / 라인 98)
  하한을 CI가 강제하는 상태로 운영.

### 프로젝트에서 배운 것 (성장 과정)

- 규칙에는 근거를 남긴다 — 아키텍처 경계는 CI로 강제하고, 지키지 못한 경계 2건은
  숨기지 않고 주석·문서·티켓으로 남겼다.
- 증상의 소유자가 원인의 소유자를 기다리면 사용자만 기다린다 — 계약을 양쪽에서 다루니
  서버 코드 진입 장벽이 낮아졌고, 크로스 스택 수정 6건으로 이어졌다.
- AI 페어 프로그래밍을 도구로 활용하되(50커밋 중 9건, 커밋 트레일러에 명시) 대형
  설계·리팩터링·물리 작업은 직접 저작 — 어디에 AI를 쓰고 어디에 쓰지 않을지의 판단도
  역량이다.
