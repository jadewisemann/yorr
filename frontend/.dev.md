## 1. 확정 기준

### 1.1 컴포넌트는 렌더링만 한다

컴포넌트 함수 본문에 남는 것: 구조분해, 한 줄짜리 파생 표시값, JSX. 그 외는 나간다.

| 무엇 | 어디로 |
|---|---|
| `useState` 여러 개가 하나의 상태를 이룰 때 | 같은 폴더의 `use<이름>.ts` |
| `useEffect` — 구독·타이머·리스너·측정 | 훅 |
| 계산·포맷·정렬·매핑 | 같은 도메인의 순수 모듈 (`duel.ts` · `court.ts`처럼) |
| API 호출 | `<도메인>/api/use*.ts` |

**판정선**: 화면·컴포넌트 파일 하나에 훅 호출(`useState`·`useEffect`·`useLayoutEffect`·`useRef`·
`useMemo`·`useCallback`·`useReducer`) **6개를 넘으면 분리 대상**이다.

순수 모듈은 React·DOM을 import하지 않는다. `yacht/domain/`에 이미 걸려 있는 규칙을
`duel/`·`pingpong/`에도 적용한다.

### 1.2 공통 컴포넌트를 내려받아 일부만 고친다

특화 컴포넌트는 공통 컴포넌트를 **다시 만들지 않고 감싼다.**

```tsx
// 좋다 — Button을 감싸 기본값만 고정한다. variant·disabled·loading·ref가 그대로 통과한다.
export function PrimaryCta({ className, ...props }: ComponentProps<typeof Button>) {
  return <Button size="cta" className={cn('w-full', className)} {...props} />
}

// 나쁘다 — 같은 모양을 <button>으로 다시 짠다. focus-ring·disabled·loading이 빠진다.
export function PrimaryCta(props) {
  return <button className="min-h-[3.625rem] rounded-panel bg-brand ..." {...props} />
}
```

- `className`은 **항상 마지막에 `cn()`으로 병합**한다. 호출자가 이길 수 있어야 한다.
- props는 `...props`로 통과시킨다. 필요한 것만 골라 받으면 확장할 때마다 파일을 고쳐야 한다.
- 새 variant가 필요하면 감싸는 쪽에 스타일을 쌓지 말고 **공통 컴포넌트의 variant map에 추가**한다.
  `Button`의 `cta` size가 그렇게 승격된 선례다.
- 배치(`w-full` · `mt-4`)는 호출부, 내부 구조와 상태 표현은 컴포넌트가 소유한다.

### 1.3 설정보다 조합

props 5개 이상으로 내부 구조를 조립하는 컴포넌트는 children을 받는 형태로 바꾼다.
`title`·`headerVariant`·`bodyPadding`·`content` 같은 props 묶음이 신호다.

### 1.4 이름

- 축약하지 않는다. `idx` → `index`, `btn` → `button`, `cfg` → `config`, `e` → `event`.
  예외는 관례가 굳은 것(`ref`·`id`·`props`)뿐이다.
- boolean은 `is`/`has`/`can`/`should` 접두. 단 HTML 속성과 짝인 것(`disabled`·`loading`)은 그대로.
- 핸들러는 prop `on<사건>` / 구현 `handle<사건>`.
- 훅 반환은 객체 구조분해. 배열은 `useState` 흉내를 낼 때만.
- **이름이 설명을 필요로 하면 이름이 틀린 것이다.** 주석을 붙이는 대신 이름을 고친다.

### 1.5 주석 — 무엇(what)은 지우고 왜(why)만 남긴다

주석을 줄이는 방법은 지우는 게 아니라 **코드가 스스로 말하게 만드는 것**이다.

지운다:

- 코드를 한국어로 다시 읽어주는 주석 (`// 상태를 초기화한다`)
- 이름을 고치면 사라지는 주석
- 내용 없는 TODO, 변경 이력

남긴다 — **다음 사람이 이 줄을 "단순화"하다 버그를 만들 수 있는 곳만**:

- 대안을 시도해서 실패한 기록 (`recipes.css`의 `@layer components` vs `@utility`,
  `cn.ts`의 `extendTailwindMerge` 목록이 왜 필요한지)
- 물리·타이밍·브라우저 특성에 의존하는 값 (`h-svh` vs `min-h-svh` 결정, iOS 주소창과 `dvh`,
  rapier 스텝과 CSS 애니메이션의 경계)
- 와이어 계약·외부 규정 (카카오 브랜드 색)

**형식**: why 주석은 **3줄 이내 한 문단.** 지금 20줄짜리 블록 주석은 그 자체가 리팩터 대상이다 —
설계 근거는 `docs/`로 옮기고 코드에는 링크 한 줄만 남긴다.

> **이 항목은 조정의 결과다.** 「주석 적게」가 요청이지만 현재 주석 중 상당수는 실제 디버깅으로
> 얻은 결론을 담고 있어서(이전 티켓의 `.dev.md`가 그 증거다) 통째로 지우면 같은 함정을 다시
> 밟는다. 그래서 **양을 줄이되 근거는 문서로 이동**시킨다. 이 판단을 뒤집고 싶으면 여기를 고친다.

### 1.6 폴더 구조 — 도메인 우선 + 세그먼트, 배럴은 쓰지 않는다

`src/` 바로 아래는 도메인, 도메인 안은 **세그먼트**다.

```
src/<도메인>/
  screens/     라우트가 그리는 화면          ← 공개
  components/  그 도메인 전용 컴포넌트        ← 공개
  domain/      순수 규칙 (React·DOM 모름)    ← 공개(타입·규칙)
  api/         REST                        ← 공개
  model/       상태·훅                     ← **비공개**
  rendering/   three.js·rapier             ← **비공개**
```

필요한 세그먼트만 만든다. 한 파일뿐이면 도메인 루트에 둔다(`sounds.ts`처럼).

**FSD와의 관계**: 세그먼트 층위는 FSD와 같은 생각이다(`ui`/`model`/`api`/`lib`).
다른 건 최상위다 — FSD는 최상위가 레이어(`app`→`pages`→`widgets`→`features`→`entities`→`shared`)고
도메인은 그 안의 슬라이스다. 진짜 FSD로 가면 `yacht/`가 세 층 이상으로 흩어져
**「레이어를 먼저 두면 야추 하나를 이해하려고 6개 폴더를 동시에 뒤져야 했다」로 기록된 그
상태로 되돌아간다.** 그래서 세그먼트만 가져오고 최상위는 도메인으로 둔다.

#### 배럴(`index.ts`)을 쓰지 않는다 — 측정 근거

배럴을 넣고 라우터의 동적 import를 배럴 경유로 바꿔 재봤다.

| | 배럴 없음 | 배럴 |
|---|---|---|
| 총 JS | 4,046,620 B | 4,048,601 B (**+0.05%**) |
| 청크 수 | 43 | 43 |
| 라우트별 분할 | 유지 | 유지 |

**번들 크기는 배럴 반대 근거가 아니다.** Rolldown이 트리셰이킹으로 되돌려 놨다.
다만 손해가 없는 게 아니라 **조건이 맞아서** 없었다 — 그 조건(부수효과 없음)이 이 저장소에
선언되지 않았다. `package.json`에 `"sideEffects": false`가 없고, 실제로 최상위 부수효과가 있다:

```
yacht/feedback/createRollFeedback.ts  new Audio('/audio/game/bowl-shake.wav') ×2
store.ts                              readRoomSession()
room/api/roomApi.ts                   new HttpRoomApiClient()
```

배럴이 `feedback/`을 재export하면 그 도메인에서 뭘 하나만 가져와도 WAV 두 개를 받기 시작한다.

**진짜 손해는 다른 데 있었다 — `check:cycles`가 눈이 먼다.**

| 실험 | dpdm |
|---|---|
| 직접 2파일 순환 | **잡는다** |
| 배럴 경유 순환(`x/impl → y/index → y/impl → x/index`) | **못 잡는다** |

그리고 이 저장소엔 조건이 갖춰져 있다 — `room/screens/GamePage` → `yacht/screens/GameResult`
→ `room/api/useGameApi`. 지금은 파일 단위라 고리가 안 닫히는데, 배럴을 넣으면 닫히고
**가드는 조용하다.**

부수적으로, 경로가 지금 담고 있는 정보도 사라진다. `@/room/api/useGameApi`는
「room의 api 층을 건드렸다」를 말하는데 `@/room`은 그걸 지운다.

#### 대신 lint로 공개 API를 강제한다

배럴이 주려던 것(도메인 공개 API)은 biome `noRestrictedImports`로 받는다.
`model/`·`rendering/`은 도메인 밖에서 import할 수 없다.

강제 범위는 측정으로 정했다 — 도메인 밖 참조 수:

| 세그먼트 | 밖에서 참조 | 판단 |
|---|---|---|
| `model/` | **0** | 강제 |
| `rendering/` | 2 | 강제 (공개 입구 신설로 해소) |
| `domain/` | 8 | 강제 안 함 — 개발 화면·mocks·`realtime/wsEvents`(기록된 예외) |
| `api/` | 12 | 강제 안 함 — `room/api/roomApi`가 사실상 공용 서비스다 |
| `screens/`·`components/` | 다수 | 공개 표면이 맞다 |

**설정에서 밟은 함정 둘**(둘 다 실측으로 찾았다):

1. `overrides`는 **누적이 아니라 교체**다. 도메인별로 규칙을 쌓으면 마지막 하나만 남는다 →
   importer 위치로 키를 잡고 서로 겹치지 않게 「자기 것만 빼고 전부 금지」를 한 항목에 담는다.
2. `patterns.group`에서 **단일 별표는 한 세그먼트만** 매칭한다. `@/yacht/rendering/*`로는
   두 단계 아래 `physics-dice/loadWorld`를 못 잡는다 → 이중 별표. 그리고 **group 안에 `!`
   예외를 섞으면 그 그룹 매칭이 죽는다** → 예외는 group 부정이 아니라 공개 입구로 푼다.

규칙이 실제로 막는지 5방향(도메인 간 금지 3 · 자기 도메인 허용 2)으로 확인했다.

### 1.6-b 임포트 경로 — 기존 규칙 유지

[`CLAUDE.md`](CLAUDE.md) 그대로: **도메인·레이어를 넘는 import만 `@/`를 쓰고 같은 폴더 안은
상대경로를 쓴다.** 세그먼트는 레이어이므로 세그먼트를 넘으면 `@/`다
(`screens/` → `@/duel/domain/duel`, 같은 폴더 → `./duel`).

테스트는 소스와 같은 폴더의 `__tests__/`에 둔다 — 세그먼트마다 자기 `__tests__/`를 갖는다.

**세그먼트 안에서 상대경로로 바꾸는 안은 버렸다.** 그러면 `@/`가 「도메인 경계」만 뜻하게 되어
lint 규칙 하나로 끝나지만, 저장소 전체에서 도메인 내부 `@/` import가 **370곳**
(`yacht`만 188곳)이다. 규칙 하나를 위해 370곳을 다시 쓰는 건 잘못된 거래다 — 설정은 한 번 쓰고
안 건드리는데 370곳은 모든 파일을 건드려 다른 브랜치와 전부 충돌한다.

컴포넌트당 폴더(`components/TaskList/TaskList.tsx`)는 **쓰지 않는다.** 한 컴포넌트가
`Foo.tsx` + `useFoo.ts` + `types.ts` + 테스트 넷 이상으로 갈라질 때만 만든다. 현재 그런 건 없다.

### 1.6-c 순수 모듈은 자기가 생산하는 타입을 소비자에게서 빌려오지 않는다

두 도메인 모두 같은 모양의 위반이 있었다. `domain/`이 자기가 **만드는** 타입을 소비자 쪽에서
import하고 있었다 — 타입 전용이라 런타임 의존은 없었지만 방향이 거꾸로였다.

| 타입 | 만드는 쪽 | 원래 선언된 곳 | 옮긴 곳 |
|---|---|---|---|
| `Outfit`·`OUTFIT_*`·`Pose` | `stage.ts` | `components/Gunslinger.tsx` (**값** 참조였다) | `duel/domain/fighter.ts` |
| `ArenaPhase`·`Fighter` | `stage.ts` | `components/Arena.tsx` | `duel/domain/fighter.ts` |
| `FrameState`·`Viewer` | `domain/localGame.ts`·`screens/PingPongGame` | `rendering/scene3d.ts` | `pingpong/domain/frameState.ts` |

결과: 두 도메인의 `domain/`이 같은 폴더와 `@/realtime/wsEvents` 외에는 아무것도 참조하지 않는다.
three.js는 `rendering/` 밖으로 나가지 않는다.

### 1.7 원시 값 금지

- 색: `bg-[#070b12]` 금지. `--ds-*` 원시값을 정의하고 `@theme inline`으로 semantic token에 연결한다.
- `text-white`도 원시값이다 → `text-content` 계열.
- 간격·반경·그림자는 토큰. 임의 값은 safe-area·fluid typography처럼 토큰화가 부적합할 때만.

토큰을 추가하면 [`src/shared/cn.ts`](src/shared/cn.ts)의 `extendTailwindMerge` 목록도 같이 고친다.
안 고치면 컴포넌트 기본값과 호출자 override가 둘 다 살아남아 승자를 CSS 선언 순서가 정한다 —
기준 1.2가 성립하지 않는다.

### 1.8 파일 크기

화면·컴포넌트 파일 **200줄 초과는 분해 대상.** 순수 모듈·테스트는 예외.

### 1.9 접근성 — 기존 수준을 낮추지 않는다

리팩터로 잃기 쉬운 것들이라 체크리스트로 둔다. 새로 만드는 게 아니라 **유지**가 목표다.

- 클릭 가능한 요소는 `min-h-tap` 이상, `<button>`/`<a>` 사용 (`<div onClick>` 금지)
- focus-visible 링을 지운 채로 커밋하지 않는다 (`focus-ring` 레시피)
- 아이콘 전용 버튼에 `aria-label`
- 상태를 색으로만 표시하지 않는다
- loading / error / empty 세 상태를 다 그린다
- 애니메이션은 `motion-reduce`에서 개별 중화한다 (전역 스위치로 끄지 않는다)

### shadcn/ui는 도입하지 않는다

- 대체 대상(`Button` 63줄 · `Modal` 115 · `Popover` 215 · `BottomSheet` 161 · `Tooltip` 135 ·
  `TextField` 55 · `ToastHost` 44 = **788줄 + 테스트 711줄**)이 이 저장소에서 **중복이 가장 적고
  테스트가 가장 촘촘한 영역**이다. `Button`은 이미 variant×size 정적 map으로 63줄이고 shadcn
  등가물은 55줄 — 8줄 아끼려고 CVA를 들이는 셈이다.
- `--ds-*` semantic 토큰과 `cn.ts`의 tailwind-merge 충돌 그룹 등록을 shadcn 토큰 체계로 바꾸면
  전 파일 마이그레이션이 딸려온다.
- 모든 오버레이가 `AnimatePresence` + `shared/motion.ts` variants로 퇴장을 그린다. Radix는
  마운트를 자기가 소유하므로 `forceMount` 수동 배선 + jsdom mock 추가가 필요하다.
- 커스텀 요구가 Radix 기본형을 벗어난다 — `Popover`의 앵커 없는 모드(랜딩 헤더 고정 자리),
  꼬리 x좌표와 `transformOrigin` 일치, 꼬리가 잘리지 않게 패널이 아니라 **내용만** 스크롤.

### 단, `Popover` 포지셔닝은 별개 티켓으로 남긴다

[`Popover.tsx:112`](src/shared/components/Popover.tsx#L112)가 `resize`만 듣고 **`scroll`을 듣지

grep이 놓친 것:

### Phase 1 — 토큰 정리 (선행 조건)

**하드 제약: 외관을 바꾸지 않는다.** 목표가 「동일한 UI」다. 그래서 기존 `positive`(`#8fcb9b`)에

**정확한 값을 보존한 채 이름만 준다.**

#### [x] Phase 1a — 흰색 알파 사다리 통합 (`duel/`·`pingpong/` 밖)

이 범위에 arbitrary hex는 0개다. 문제는 같은 사다리가 두 벌 적혀 있는 것:

| 값 | 앱 네임스페이스 | landing 네임스페이스 | 사이트 |
|---|---|---|---|
| `white/10` | 토큰 `border` | `landing-hairline` (**같은 값**) | 정의 중복 |
| `white/18` | **토큰 없음** | `landing-hairline-strong` (**같은 값**) | **12곳** |
| `white/14` | **토큰 없음** | 없음 | **7곳** |
| `white/6` | 토큰 없음 | `landing-soft`(7% — 1% 차이) | 5곳 |

`landing-*`가 별도인 이유는 랜딩 팔레트가 다르기 때문인데, **중성 흰색 알파 hairline은 팔레트가
아니라 같은 사다리를 두 번 적은 것**이다. 색 토큰은 네임스페이스를 유지하고 **hairline 사다리만
합친다.** `tokens.css`의 「반투명 패널·헤어라인은 랜딩에서만 쓰므로」주석은 이제 사실이 아니다 —
`white/18`이 랜딩 밖 12곳에서 쓰인다.

신설 토큰 3개 (전부 기존 값과 **정확히 일치**하므로 외관 변화 0):

| 토큰 | 값 | 역할 | 사이트 |
|---|---|---|---|
| `border-raised` | `white/14` | 떠 있는 표면의 경계 — 시트 상단, 툴팁, 칩, 점선 빈자리 | 7 |
| `border-strong` | `white/18` | 강조·선택 상태 경계, 그리고 1px 구분선 | 12 |
| `surface-veil` | `white/6` | 캔버스 위 아주 옅은 칩·배너 바닥 | 5 |

`--ds-landing-hairline`/`-strong`는 신설 원시값을 참조하게 바꾼다 — **호출부를 건드리지 않고
정의만 하나로 만드는** 단계다. 6%와 7%는 합치지 않는다(1% 차이지만 외관 보존이 우선).

`cn.ts`는 **고치지 않는다.** 그 파일 주석이 이미 말한다 — 「색 토큰은 tailwind-merge의 색
validator가 임의 이름을 받아주므로 등록하지 않아도 병합된다」.

**완료 조건**: `duel/`·`pingpong/`·`app/dev/`·QR·three.js 밖에서 `white/(6|14|18)` 0건.

#### [x] Phase 1b — **214로 대체됨**

`refactor/214-ui-redesign`이 이 범위를 이미, 그리고 더 잘 했다(병합 커밋 `8697274`).

214가 만든 것: `pp-*` 12개 + `duel-*` 8개 팔레트, `text-2xs`(11px, 손으로 적던 9·10·10.5·11px
64곳을 대체), 라운드 사다리 양 끝(`chip` 6 · `hero` 32), `--breakpoint-tray`(400px), 필름 그레인,
`Button`의 pressed 상태.

**핵심은 판단의 차이다.** 내가 「외관 보존」을 하드 제약으로 걸고 미룬 것을 214는 **의도적으로
작은 외관 변화를 받아들여 실제 결함을 고쳤다**:

- 탁구의 빨강 2색(`#e2513c`·`#ff8b7c`)이 시스템 `brand`·`brand-soft`와 RGB 거리 25·10이라
  나란히 놓아도 구분되지 않았다 → 시스템 색으로 흡수. 「구분되지 않는 색이 둘이면 그건
  팔레트가 아니라 실수다」
- 결투의 앰버 4색이 Tailwind 기본 팔레트(amber-500/400, green-300, red-300)를 붙여넣은 값이라
  채도 92~100%로 서로 경쟁하고 있었다 → H35 한 줄기(L81 → L77 → L55)로

그쪽이 맞다. **외관 보존은 리팩터의 기본값이지만 절대 규칙은 아니다** — 보존하려는 그 외관이
이미 결함이면 보존이 결함을 굳힌다. 다만 그 판단은 근거를 적고 해야 한다(214는 RGB 거리와
채도·명도를 적었다).

내 작업 중 214에 흡수된 것: `--ds-pingpong-canvas` → 214의 `--ds-pp-canvas`(호출부 13곳),
중복 `--ds-duel-canvas` 제거(두 브랜치가 같은 이름·같은 값을 독립적으로 만들었다).
three.js 짝 주석은 214의 `pp-canvas` 자리로 옮겼다 — 그 불변식은 여전히 유효하다.

토큰화했는데 214는 값 자체를 `white/28`로 올렸다 — white/18은 캔버스 위 1.62:1로 **비활성**
Primary(2.10:1)보다 흐리다는 근거가 붙어 있다. 값이 이기고 토큰화는 물러난다.

| **단일 뷰포트 화면** `h-svh` + `overflow-hidden` | `LobbyPage` · `GameResult` · `LeveragePage` · `EntryPage`×2 · `PingPongModePage` · `PingPongGame`×3 · `DuelGame`×3 · `DuelController` · `PingPongController`×2 (16) | `max-w`, 배경, `touch-none`/`select-none` |
| **게임판** `mx-auto h-svh w-full max-w-play overflow-hidden bg-canvas text-content` | `GamePlay` · `PartyDashboardPage` · `PartyResultDashboard` (3) | **없다 — 문자열이 완전히 동일하다** |
| **중앙 정렬 상태 화면** | `ScreenFallback` · `AuthCallbackPage` · `DuelGame:258` · `PingPongGame:171` (4) | 배경, `role`/`aria-busy` |

`shared/components/Screen.tsx`에 `<Screen>`을 두고 네 가족을 variant로 받는다. `max-w`·배경은
props가 아니라 `className`으로 확장한다(기준 1.2). **safe-area 패딩 계산은 컴포넌트가 소유한다** —
지금 25곳이 각자 `pb-[max(1.25rem,env(safe-area-inset-bottom))]`를 손으로 쓰고 있다.

`h-svh` vs `min-h-svh` 결정은 **바꾸지 않는다.** 이 앱의 모든 화면은 정확히 한 뷰포트를 프레임으로
잡고 `GamePlay`의 3D 트레이가 그 프레임에 맞춰 크기를 정한다. 근거는 이전 티켓의 결정 기록에 있고,
`Screen.tsx`에 링크 한 줄로 남긴다(기준 1.5).

**완료 조건**: `env(safe-area-inset` 문자열이 `Screen.tsx`와 토큰 밖에 나타나지 않는다.

### [~] Phase 3 — 생 `<button>` 수렴 (진행 중)

**터치에서 손가락이 닿았다를 알리는 유일한 채널이 빠진 상태**다. 착수 시 실측: 68곳 중

#### [x] 3a — 알약 7곳 → `GameChromeButton` (`006924c`)

`Button`을 감싸 pressed·focus-ring·min-h-tap·disabled를 함께 받는다. `tone`은
`canvas`(단색 위) / `overlay`(살아 있는 3D 렌더 위 — 스크림 + 블러) 둘이고, 위치는 `className`이다.

`font-normal`을 남겼다 — 일곱 자리 전부 굵기를 지정하지 않아 본문 굵기를 물려받고 있었다.
굵게 올리는 것은 게임 화면의 시각 결정이라 이 리팩터에서 하지 않는다.

#### [x] 3b — pressed 누락 10곳 (`60d95fc`)

공유 const **두 줄**로 10곳이 함께 났다.

- `AccountDialog`의 `row` (6곳) — focus ring·탭 하한은 있었고 pressed만 없었다
- `LandingHeroCard`의 `playCta` (2곳) — **이 앱에서 가장 많이 눌리는 자리**인데 터치에서
  누른 순간 아무 반응이 없었다

`lockedCta`·`lockedRow`는 제외했다(누를 수 없는 상태).

#### [x] 3c — 팝오버 헤더 · 게임 버튼 상태 (`2e1d7fe` `78ae8ad`)

**팝오버 제목 줄 → `PopoverHeader`.** 초대·오디오가 같은 여덟 줄을 각자 썼다. 그 안의 닫기는
`p-0`이라 **12px 글자 높이가 곧 탭 영역**이었다(약 16px) — 규칙 4 위반. 44px로 만들고 제목 줄
높이는 음수 마진으로 유지했다. 브라우저 실측: 제목 줄 27.1px(변화 없음), 닫기 `min-height` 44px,
패널 오른쪽 여백 23.8px로 넘치지 않음.

닫기를 `Button`으로 바꾸지 않은 이유: 굵기·gap·라운드·transition을 거의 다 덮어써야 한다.
그건 `Button`을 쓰는 게 아니라 흉내내는 것이다.

**게임 버튼 8곳에 `focus-ring`·pressed 추가.** 권한 켜기(듀얼 2 · 탁구 3) · 준비 완료 ·
듀얼 안내 버튼 2곳이 둘 다 없었다. 브라우저 기본 포커스 링에 의존하고 있었는데 이 프로젝트는
`focus-ring` 레시피로 3px 실선을 표준으로 정해 뒀다.

**컴포넌트로 뽑지 않았다** — 같은 모양은 2곳뿐이고 나머지는 각자 크기·라운드·글자가 다르다.
2곳은 새 컴포넌트 기준에 못 미친다.

**`PingPongModePage`의 뒤로 가기 → `GameChromeButton`.** canvas tone과 색이 같았다
(`bg-white/6` == `bg-surface-veil`). `text-white/75` → `/70`은 구분되지 않는 드리프트다.

갈린다. 부드럽게 할 자리는 자기 `transition` 목록에 `scale`을 넣는다(`Button`이 그렇다).

0.97은 24px에서 0.7px라 보이지 않는다. 레시피에 두 번째 단을 만들 만큼 잦지 않다.

#### [ ] 3d — 판단을 남긴 것

생 `<button>` **61곳**. 여기서 중요한 판단: **전부 `Button`으로 바꾸는 것은 틀렸다.**

### 5번 — 정정

「라운드 리셋은 렌더 중 조정, 턴 리셋은 effect라 방식이 갈린다」고 적었는데, 읽어 보니 **같은
종류의 리셋이 아니다.**

- 라운드 리셋: `roundNumber`에서 나오는 **순수 파생**이다. effect로 미루면 새 라운드의 첫
  프레임에 지난 라운드 주사위가 스친다 → 렌더 중 조정이 맞다.
- 턴 리셋: 「새 턴의 주사위 방송이 턴 교체보다 먼저 도착했는가」를 보고 결정하는 **정리**다.
  판단 근거가 메시지 도착 순서이고 in-flight ref 넷을 함께 비운다 → effect가 맞다.

그래서 통일하지 않았다. 되돌리기를 `resetLocalFor` 하나로 모으고 조건에
`diceForThisTurnAlreadyArrived`라는 이름을 줘서 **왜 다른지가 읽히게만** 했다.

### 3번 — 함께 고친 잠재 버그

`useImpactDelay`가 「내 총알이 이미 날아간 만큼」을 깎을 때 라운드를 보지 않았다. 시간 초과로
진 라운드는 `foulId`가 나지만 쏜 적이 없어서, **지난 라운드의 발사 시각으로 재고 즉시 착탄**이
됐다. 렌더 쪽(`DuelGame.tsx`)이 이미 쓰던 `myShot?.round === state.round` 가드를 여기도 건다.

### 남은 것 — 렌더 중 ref 12곳

전부 이벤트 핸들러나 rAF 루프에서 읽는 「최신 값」ref다(`useAsyncTask`의 `taskRef`,
`useGamePlayRoll`의 `renderedGameRef`, `usePhysicsDiceWorld`의 `latestRef` …).
**Effect Event는 effect 안에서만 호출할 수 있어 대상이 아니다.** 정석대로 하려면 `useDuelGame`처럼
`useLayoutEffect`로 옮기면 되고, 얻는 것은 규칙 준수뿐이라 별건으로 남긴다.

### `useGamePlayRoll` 수신부를 떼지 않은 이유

`handleBroadcast` 외 네 핸들러가 굴림 상태 기계의 setter 5개와 in-flight ref 4개를 직접
건드린다. 떼면 그 열 개를 인자로 넘기게 되는데, 그건 2번에서 없앤 자루를 이름만 바꿔 다시
만드는 일이다. **이 파일을 더 가르려면 상태 기계 자체를 리듀서로 올려야 하고, 그건 실시간
타이밍이 걸린 별도 티켓이다.**
