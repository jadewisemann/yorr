## A. 전체

### [x] A-1. 태블릿 브레이크포인트 도입

**현재 상태.** 브레이크포인트가 각 화면에 문자열로 흩어져 있다 — 랜딩은
`EntryPage.tsx`의 `WIDE_LAYOUT = '(min-width: 760px)'`, 게임은 `GamePlay.tsx`의
`(min-width: 1024px)`. 그 사이(760–1199px, 즉 태블릿 가로·작은 노트북)를 위한 단계가
아예 없어서 랜딩은 760px을 넘는 순간 **1440px용 데스크톱 레이아웃**을 그대로 쓴다.
B-1·B-2의 원인이 전부 이것이다.

**어떻게.** Tailwind v4는 `@theme`의 `--breakpoint-*`가 곧 variant다. `styles/tokens.css`에
단계를 정의하면 CSS variant(`desktop:`)와 JS 미디어쿼리가 같은 값을 공유한다.

```css
--breakpoint-desktop: 75rem; /* 1200px — 헤더가 한 줄에 다 서는 하한 */
```

- 760px은 **DOM 구조가 갈리는** 지점이라 그대로 `useMediaQuery`로 남긴다(모바일은 스와이프
  + 바텀시트, 데스크톱은 팝오버 — 구조가 다르다).
- 1200px은 **스타일만 갈리는** 지점이라 JS 분기를 만들지 않고 `desktop:` variant로 처리한다.
  `useMediaQuery`를 하나 더 붙이면 리렌더가 늘고 테스트에서 또 mock해야 한다.

**손대는 곳**: `src/styles/tokens.css`, `src/landing/screens/EntryPage.tsx`

### [x] A-2. 텍스트 필드 욕설·외설 검증을 공용으로 묶고 리팩터링

**현재 상태.** 닉네임 검증이 두 벌이다.

- `auth/nickname.ts`의 `getNicknameError()` — 길이·허용문자 검사. `NicknamePage`가 쓴다.
- `AccountDialog.tsx`의 `NicknameEditor` — `value.trim()`이 비었는지만 본다. 여기서는
  길이도 허용문자도 안 본다. 공용 `TextField`도 안 쓰고 `<input>`을 직접 그린다.

즉 **프로필 닉네임 변경 경로에는 검증이 사실상 없다.** 욕설 필터를 `NicknamePage`에만 넣으면
이 경로로 그대로 빠져나간다.

**어떻게.**

1. `src/shared/profanity.ts` 신설 — 금칙어 목록 + `containsProfanity(value)`.
   비교 전에 공백·특수문자를 지우고 소문자로 정규화한다(`ㅅ.ㅂ`, `s h i t` 우회 차단).
2. `getNicknameError()`에 욕설 검사를 한 줄 추가한다 — **모든 호출자가 여기로 모이므로
   검사를 붙일 자리는 여기 하나다.**
3. `NicknameEditor`의 검증을 `normalizeNickname` + `getNicknameError()`로 갈아끼운다.
   이제 프로필 변경도 방 입장과 **같은 규칙·같은 문구**로 막힌다.

`NicknameEditor`의 `<input>` 마크업은 공용 `TextField`로 바꾸지 않았다. `TextField`는
전체 화면 폼용(`min-h-14`, `rounded-card`, `bg-surface`)이라 좁은 팝오버 한 줄에 넣으면
디자인이 달라진다 — QA가 요청한 것은 검증의 공용화이고, 시각 변경은 범위 밖이다.

우회를 완벽히 막지는 않는다(자모 분해, 초성, 유사 글자 치환). 서버에도 같은 검사가 있어야
하는 종류의 검증이고, 프런트는 "실수로 튀어나오는 것"을 막는 층이다 — 목록이 부족하면
`profanity.ts`에 단어만 추가하면 된다.

**손대는 곳**: `src/shared/profanity.ts`(신설), `src/auth/nickname.ts`,
`src/auth/components/AccountDialog.tsx`

### [x] B-2. 1200px 아래에서 상단 레이아웃이 옆으로 밀림

**원인.** wide 헤더는 한 줄에 다섯 덩어리를 세운다 — 워드마크 · 구분선 ·
h1(`링크 하나로 모이면 바로 시작하는 파티 게임`, `whitespace-nowrap`) · 초대 코드 버튼 ·

**어떻게.** A-1의 `desktop:`(1200px) 아래에서는 h1과 그 앞 구분선을 감춘다. 랜딩의 가치

### [x] B-3. 모바일 히어로 좌우의 pointer 객체가 상단 내비와 안 맞음

**실측(390px).** 헤더 워드마크는 20px, 초대 코드 버튼 오른쪽 끝은 370px. 히어로 카드는
`inset-x-[9%]`라 35.1 ~ 354.9px에 서서 **양쪽 15px씩 안으로 들어와** 있었고, 그 안쪽
37.1 / 308.9px에 pointer가 달린 `ArrowButton`(‹ ›)이 붙어 있었다. 이웃 카드(`PeekCard`)는
`pointer-events-none`이라 해당 없다.

**어떻게(사용자 결정).** 화살표는 **그대로 두고 카드 거터만 맞춘다** —
`inset-x-[9%]` → `inset-x-5`(헤더와 같은 고정 20px). 퍼센트는 뷰포트마다 값이 달라져
어느 폭에서도 헤더와 같은 세로선에 설 수 없다. 결과: 카드 20 ~ 370.1px, 워드마크 왼쪽
끝·코드 버튼 오른쪽 끝과 정확히 일치.

**받아들인 비용.** 이웃 카드가 내보이는 폭이 35px → 20px로 줄었다. 보이는 양은 카드
가장자리와 뷰포트 가장자리 사이 거리라 **거터를 20px로 맞추면 20px이 되는 것이 필연**이다
(peek 카드 폭을 키워도 달라지지 않는다). "옆에 더 있다" 신호가 그만큼 약해진다 —
문제가 되면 거터를 다시 벌리는 것 외에 방법이 없다.

띠가 미끄러지는 거리(`SLIDE_DISTANCE_PCT`)는 손대지 않았다. 카드가 가운데 서므로(중심 50%)
그 값을 정하는 것은 peek 좌표뿐이고, peek는 그대로다. 실제로 전환 시 `translateX(53.3%)`가
그대로 나오는 것을 확인했다.

**손대는 곳**: `src/landing/components/LandingHeroCarousel.tsx`

### [x] B-7. 진입 직후 방향키로 히어로가 안 움직임

**원인.** 방향키 처리기가 두 군데 있는데 **둘 다 포커스를 받아야 동작한다.**

- `LandingHeroCarousel`의 `<section onKeyDown>` — `<section>`은 `tabIndex`가 없어 포커스를
  받을 일이 아예 없다. 사실상 죽은 코드다.
- `LandingProgress`의 tablist — 여기에 탭으로 들어가야 방향키가 먹는다.

진입 직후 포커스는 `<body>`에 있고, Tab을 누르면 문서 순서상 상단 헤더가 먼저 잡힌다.
그래서 "방향키를 눌러도 아무 일이 없다"가 된다. **내비에 시멘틱 태그를 달아도 해결되지
않는다** — 문제는 랜드마크 구조가 아니라 "포커스가 캐러셀에 없다"이다.

**어떻게.** 랜딩이 살아 있는 동안 `document`에 방향키 리스너를 하나 단다.

- `event.defaultPrevented`면 무시한다 → tablist가 이미 처리한 키를 두 번 세지 않는다.
- 이벤트 대상이 `input` · `textarea` · `contenteditable`이거나 `[aria-modal="true"]` 안이면
  무시한다 → 코드 입력 다이얼로그·바텀시트가 열려 있을 때 뒤의 캐러셀이 같이 움직이지 않는다.
- 죽어 있던 `<section onKeyDown>`은 지운다. 두 경로가 동시에 살아 있으면 한 번 누를 때
  두 칸 넘어간다.

진입하자마자 특정 요소에 `focus()`를 걸지는 않는다 — 사용자가 아무것도 안 눌렀는데 포커스
링이 화면에 나타나고, 스크린리더는 그 지점부터 읽기 시작한다.

**손대는 곳**: `src/landing/components/LandingHeroCarousel.tsx`

## C. 대기실

### [x] C-1. 게임 시작 전환 로딩 모달

**현재.** "게임 시작"을 누르면 버튼 안 스피너만 돌고, 서버 `state.sync`로 phase가 바뀌면
그때 라우터가 게임 화면으로 옮긴다. 참가자(호스트가 아닌 사람)에게는 **아무 신호도 없이**
화면이 바뀐다.

**어떻게.** `src/shared/components/LoadingOverlay.tsx`를 새로 만든다 — 스크림 + 스피너 +
문구뿐인 블로킹 오버레이다. 기존 `Modal`을 쓰지 않는 이유: `Modal`은 제목 줄과 닫기 버튼을
전제로 하고 포커스를 닫기 버튼에 준다. 닫을 수 없는 전환 상태에 닫기 버튼을 그리게 된다.

대기실에서 띄우는 조건은 **`roomSnapshot.phase !== 'waiting'`** 하나로 잡는다. 호스트의
"눌렀다"와 참가자의 "호스트가 시작했다"가 같은 신호라 조건이 하나로 끝나고, 화면 이동은
어차피 이 phase 변화가 만든다.
