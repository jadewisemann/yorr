# ADR-0007: 게임 모듈의 공통 뼈대를 뽑는다

- 상태: 채택
- 날짜: 2026-09-01

## 맥락

게임 슬라이스를 하나씩 채우는 방식(DESIGN.md 「게임 하나 = 수직 슬라이스」)으로 결투 ·
탁구 · 다빈치 코드가 차례로 들어왔다. 세 게임은 서로를 보고 만들어졌고, 그 결과 같은
코드가 세 벌 생겼다. jscpd(50토큰 기준)가 센 것만 보면 이렇다.

| 자리 | 겹친 줄 |
|---|---|
| `*GameModule`의 수명주기 위임 · 멤버십 검사 · 오류 봉투 | 83 + 37 |
| `*StateStore`의 SETNX 초기화 · 방 단위 락 · TTL 복사 · version 판정 | 36 + 19 |
| 점수 기록 어댑터 | 12 |

복제 자체보다 **갈라질 위험**이 문제다. 셋 중 하나에서 락 해제 조건이나 version 판정을
고치면 나머지 둘은 조용히 옛 동작으로 남는다. 실제로 탁구만 version 판정이 `===`이고
나머지 둘은 `<=`였다.

## 결정

게임에 **무관한 것**만 공통으로 올린다.

- `game/socketGameModule.ts` — 수명주기 일곱 훅의 위임, 멤버십·roomId 검사, `error`
  봉투 전송. 게임이 채우는 자리는 `handles`·`dispatch`·`start`·`reconnect`뿐이다.
- `game/versionedStateStore.ts` — SETNX 초기화, 방 단위 락(SET NX + 토큰 비교 해제),
  방 키 TTL 복사, version 비증가 갱신 폐기.
- `game/score/rosterScoreWriter.ts` — 명단에 남아 있는 사람의 점수만 기록.

**게임마다 다른 것은 올리지 않는다.** 상태 키, 저장 값의 검증, 오류 코드 문자열,
어떤 예외를 도메인 오류로 볼지(탁구는 `DomainError`만, 나머지는 `CodedError`),
`find`가 없음을 무엇으로 표현할지(탁구는 `undefined`, 나머지는 `null`)가 그렇다.
이것들은 옵션이나 훅으로 받는다.

## 결과

- 프로덕션 중복이 40쌍에서 줄었고, 세 게임의 락·version 판정이 한 곳에서 정의된다.
- 새 게임을 붙일 때 채울 자리가 서명에 드러난다.
- 탁구의 version 판정이 `===`에서 `<=`로 바뀌었다. 후자가 상위집합이라 version이
  줄어드는 갱신을 추가로 막는다 — 기존 검사 84건이 그대로 통과한다.

## 대안

**그대로 둔다.** 세 게임이 서로 독립이면 갈라져도 상관없다는 입장이다. 그러나 갈라진
것이 락 해제 조건이라면 한 게임에서만 상태가 덮어써지고, 그 증상은 "가끔 점수가
되돌아간다"로 나타나 재현이 어렵다.

**게임 서비스까지 공통 기반으로 올린다.** 하지 않았다. 서비스는 게임 규칙이 사는
자리이고, 지금 겹쳐 보이는 것(방송 · 마감 예약 · 종료 판정의 순서)도 게임이 하나 더
들어오면 갈라질 가능성이 높다. 뼈대는 **세 번 같은 것을 본 뒤에** 뽑는다.
